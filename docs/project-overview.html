Fabric PPC — what it is, how it works, how to run it

A production-tracking application for the Production Planning & Control team of a textile dyeing, printing and finishing mill. It replaces paper floor sheets, a macro-driven Excel tracker and manual Oracle re-entry with one ledger of every metre of every lot. Status as of 22 Sep 2026.

1 · What it is

  • Problem it replaces: triple entry — handwritten floor production sheets → re-typed into Fabric Report.xlsm → contract/lot master data held separately in Oracle EBS; the three never agree and reconciling is manual.
  • Goal: track every lot through every operation from greige receipt to dispatch; show live status per PO and lot (in stock / at which step / finished / dispatched / lost); gate dyeing and printing on colour approval; record dispatch and closing; reproduce the mill's Month Wise Fabric Report exactly.
  • Success: PPC no longer maintains the Excel tracker.
  • Users: PPC staff and department managers (most data entry), department in-charges (own department only), colour lab, dispatch/inspection, viewers, an admin.
  • Look & feel: deliberately behaves like Oracle Forms (toolbar, query mode, LOV pop-ups, function keys, status line) because staff already use Oracle EBS daily; reports follow Oracle Reports conventions. English by default, Urdu with full RTL.
  • Source of truth split: Oracle owns contract/lot master fields (imported from the "Processing Contract Status [Party Wise]" Excel export, later via API behind the same interface); the app owns all progress. A lot missing from a later export is flagged, never deleted.

Key decisions (D1–D16, spec §2)

  • D1/D2 Oracle export upload now, API later; Oracle owns master data, app owns progress. D3 Oracle QNTY is the greige received ("ERP Load").
  • D4 seven roles, admin-editable permissions. D5 anyone permitted can edit at any time; every change audited (who, when, old → new).
  • D6 each lot gets a planned route from a template chosen by PO type + quality, editable per lot; reprocess and unplanned steps allowed. D7 a machine batch can hold several lots; a batch total splits proportionally and stays editable. D8 quantity is tracked per stage position, so one lot can be spread over several stages.
  • D9 Oracle issues the challan; the app records dispatch. D10 manual lot close; the remainder becomes a recorded loss with a reason. D11 colour gate warns; PPC/Manager may override with a logged reason. D12 status codes are editable lookups seeded from the tracker.
  • D13 movement ledger + live balances table. D14 stack below. D15 Oracle-Forms UX. D16 English + Urdu/RTL.

3 · Architecture

  • Modular monolith. One Laravel app; each module owns its models, migrations (reserved numeric ranges), services, controllers, Vue pages and tests under app/Modules/<Module>/….
  • Only a module's own services write its tables. Other modules call those services. Production\Services\LedgerService is the single writer of lot_movements, lot_balances and the lot's derived quantity/label columns.

Request path

  • routes/web.php requires settings.php then every file in routes/modules/*.php (foundation.php, oracle.php, production.php; inquiry.php arrives with P2 Task 11). Explicit routes always sit above generic catch-alls.
  • Every route is behind auth + verified + Spatie permission:<name> middleware; department scoping is enforced in policies via department_user. The UI only hides what the server already forbids.
  • HandleInertiaRequests shares auth.user / roles / permissions / departments, locale, dir (ltr/rtl), i18nVersion; Vue reads them through @/lib/can.ts and @/lib/i18n.
  • Toasts: Inertia::flash('toast', […]) then back()/redirect(); the kit's flashToast.ts listens on Inertia's flash event. Record auto-select after save uses a flashed selectedId.
  • Unexpected errors: logged with a 10-hex reference id (ErrorReference, WeakMap per exception) and rendered as the Error Inertia page carrying that id — XHR and full-page loads alike.

i18n

  • PHP lang files per module group (lang/en|ur/{app,auth,forms,masters,admin,oracle,production,settings,…}.php); served as cached JSON at GET /i18n/{locale}.json?v=; inlined on first load as window.__I18N__.
  • t('group.key', replacements) reads a shared reactive dict; initializeLocaleSync() reloads on every Inertia navigation when locale/version differ; a late response for a superseded locale is discarded.
  • Urdu sets <html dir="rtl">; layouts use Tailwind logical properties. Numbers and dates stay Latin/Gregorian.

4 · Data model (essentials)

Foundation

  • departments 12 cost centres (Batching-Stenter … Stitching)
  • machines per department
  • operations 112 seeded; kind normal|reprocess, stage_label (e.g. BLEACHING/), counts_as_finish_production, finish_type null|dyed|print, is_stretch
  • shifts A/B · parties (+party_aliases) · qualities (parsed ends/picks/counts/composition)
  • route_templates + route_template_steps (po_type, quality LIKE pattern, priority)
  • lookup_values lists: colour_status (with meta.approved), po_type, loss_reason, hold_reason, reprocess_reason
  • settings (string key → JSON; e.g. default_route_template_id), audits, Spatie tables, department_user

OracleSync

  • oracle_imports status: previewed → committing → committed | failed | discarded; counts new/changed/unchanged/missing/errors
  • oracle_import_rows action per row, JSON payload + field diff, error message (unknown_party:, overlong:, bad_row:, greige_below_issued:, duplicate_line:)
  • Match key: Oracle PC_DTL_ID → lots.oracle_line_id (unique). LOT_NUM1 is not unique across POs.

Production

  • contracts po_no (unique), party, ref_no, po_date, contract_qty, oracle_missing_at
  • lots Oracle fields (lot_no, contract, quality, gsm, design, colour, widths, po_type, greige_qty) + app fields (colour_status, state open|hold|closed|cancelled, hold/cancel/loss reasons, state_changed_at) + derived (stock_qty, issued_qty, wip_qty, finished_qty, dispatched_qty, loss_qty, current_label, last_movement_at — written only by the ledger)
  • lot_route_steps seq, operation, is_added, status pending|partial|done|skipped
  • lot_movements insert-only ledger (see §5) · lot_balances (lot, position, qty; unique)
  • production_sheets date+shift+machine (unique), department, downtime, remarks · production_lines batch_no, lot, step, operation, is_reprocess+reason, qty_in, qty_out, output_type, widths · colour_overrides one per line, reason, approved_by/at
  • Audited models ("(A)" in the spec): every Foundation master, Contract, Lot, LotRouteStep, ProductionSheet, ProductionLine, ColourOverride. Not audited: Setting (string PK), LotMovement/LotBalance (the ledger is the trail) and the lot's derived columns (query-builder updates).
  • Indexes from spec §9: lots(lot_no), lots(contract_id, state), lots(state, current_label), lot_balances(lot_id, position), lot_movements(lot_id, moved_at), production_lines(lot_id), production_sheets(sheet_date, machine_id, shift_id).

5 · The ledger — how every metre is tracked

Positions

STOCK→ISSUED→STEP:<route_step_id> …→FINISHED→DISPATCHED/LOSS
  • STOCK greige received, not issued · ISSUED on the floor before the first step · STEP:<id> completed that step, waiting · FINISHED completed the last step · DISPATCHED/LOSS terminal counters.
  • Positions derive from the lot's route, bypassing skipped steps; a route edit may not move metres already sitting at a progressed step's position (position-stability guard).

Movement kinds and enforced shapes

kindfrom → toPosted by
import∅ → STOCK (qty = greige_qty)Oracle commit (inside its transaction) or production:backfill-ledger
adjustmentexactly one side ∅, other non-terminal (greige change, override shortfall)import, override path
issueSTOCK → ISSUED (partial allowed)Issue to Floor (per lot / bulk per PO)
processISSUED|STEP:n → STEP:m|FINISHED (from ≠ to), or in place at a non-terminal non-STOCK position (unplanned work)Production sheet line
reprocessfrom = to, non-terminal, non-STOCK (FINISHED→FINISHED allowed)Production sheet line flagged reprocess or a reprocess-kind operation
dispatchFINISHED → DISPATCHEDP3
lossnon-terminal → LOSSP3 close

Rules

  • qty_out_of_from and qty_into_to are stored separately, so gain/shrink per operation is kept (e.g. stenter 3,578 → 3,627).
  • No position may go negative. InsufficientQuantity carries the available figure; a user with production.override may supply a reason, which posts an adjustment first (postWithOverride()).
  • Edits and deletes never mutate a movement: they post a reversal (reversal_of_id, unique — one reversal per movement, a reversal cannot be reversed) plus a new movement; balances and lot totals are recomputed in the same transaction.
  • Every ledger write: DB::transaction → lockForUpdate the lot row → lock its balance rows → locking reads for every figure that feeds a write (InnoDB REPEATABLE READ would otherwise serve a stale snapshot inside a caller's transaction) → insert → balance deltas → totals + status label in one update. Lock order everywhere: lot → balances → movements → route steps.
  • Floor movements (issue/process/reprocess) need state = open (LotNotOpen); reversals, adjustments, loss and dispatch don't.
  • Invariant (checked by tests and the nightly CheckLedgerInvariant job at 02:00): per lot, balances = Σqty_into_to − Σqty_out_of_from per position, and the six lots.*_qty columns equal the balances. rebuild() repairs from the movements.
  • Derived values: Greige In Stock = STOCK · Qty Issued = net metres issued out of STOCK (ruled; spec text said greige − STOCK) · WIP = ISSUED + ΣSTEP · Finished = FINISHED · Dispatch = DISPATCHED.

Status label (lots.current_label, first rule that applies)

  • 1 CANCELLED/ or HOLD/ from state · 2 closed → DISPATCHED/ if anything dispatched else CLOSED/ · 3 any standing dispatch on an open lot → DISP dd-mm-yy/ (last un-reversed dispatch) · 4 stage_label of the next pending step for the largest WIP portion (skipped steps bypassed; WIP/ if no route) · 5 RF-INSP/ when FINISHED > 0 and nothing on the floor (STOCK may remain) · 6 blank while everything is in STOCK.
  • Process flag: Complete when closed or cancelled, or when STOCK+WIP+FINISHED = 0 and greige > 0; otherwise Pending.

6 · How work flows

Oracle import (OracleSync)

  • Upload the XLSX → headers validated → rows parsed by ExcelUploadSource (bad rows become bad_row error rows, not a failed upload; per-field length limits → overlong).
  • Preview classifies each row by PC_DTL_ID: new / changed (field diff) / unchanged / missing / error. Parties resolve by oracle_code → normalised name → alias; unmatched ones must be linked or created (one Oracle code per party). A greige decrease below what has left STOCK is an error row (greige_below_issued).
  • Commit: controller checks + atomic previewed → committing, then the queued CommitOracleImport job takes Cache::lock('oracle-import-commit', 660)->block(300) and runs one transaction: parties, qualities, contracts, lots; for each new lot LotIntakeService::receive() assigns the route (template matcher → default-template setting) and posts the import movement; greige changes post an adjustment. Missing lots/contracts get oracle_missing_at (cleared when they reappear). Events fire after commit. Failure → failed + message; commit blocked while error rows exist.
  • CLI: php artisan oracle:import {path} [--user=] [--commit]. Existing lots without a ledger: php artisan production:backfill-ledger [--user=] (idempotent).

Planning (Production)

  • Lot Route editor (production.route.manage): edit steps, add is_added steps, reorder, skip/unskip, apply a template to a lot or to every open lot of a PO. Steps with production are locked (order, operation, removal); edits that would move metres already at a completed step are refused with a translated reason.
  • Issue to Floor (production.issue): per lot with a lot LOV (full no., last 4 digits or PO; shows PO + design + colour; in-stock lots only) or "issue all stock of this PO" (shows open-lot count and stock first).
  • Hold / release / cancel (production.hold): reasons from the hold_reason list; cancel only when nothing is in WIP/FINISHED; held/cancelled lots refuse floor movements.

Production entry

  • One sheet per date + shift + machine; the machine's department limits the operation LOV and the offered route steps; department in-charges may only save their own department's sheets (production.sheet.edit.own_department via department_user).
  • Line resolution: explicit step (must belong to the sheet's department) → the pending/partial step of the line's operation in that department → the department's next pending step → last step of that operation → unplanned (posted in place, step null). Reprocess lines post in place at the step's target.
  • Batches: lines sharing a batch_no form one run; "split batch total" spreads a total in proportion to available metres (2 dp, remainder on the largest line; editable afterwards).
  • Colour gate on save: operation in Jigger Dyeing/Printing or with finish_type on a lot whose colour_status is not flagged approved → blocking; a user with colour.override.approve may supply a reason, logged in colour_overrides (kept even if the colour is approved later).
  • Totals per sheet (fresh / reprocess / stretching / total, per output type dyed/print/other) are computed server-side and mirrored client-side.
  • Editing a saved sheet re-posts only changed lines (plus later lines of the same lot); ledger-neutral fields update in place; a line whose metres have already moved on cannot be edited or deleted.

10 · Tests and the verification gate

  • Every change must pass all of: ./vendor/bin/pest · npm run test:js · npm run types:check (vue-tsc) · npm run build · composer ci:check (vp format+lint, vue-tsc, pint, phpstan, pest) · ./vendor/bin/phpstan analyse with no new phpstan-baseline.neon entries. Run npx vp check --fix and ./vendor/bin/pint before committing.
  • phpunit.xml points Pest at in-memory SQLite. On a PHP build without pdo_sqlite (this dev box) run against a scratch schema on the Docker MySQL instead — never the .env database:
DB_CONNECTION=mysql DB_HOST=127.0.0.1 DB_PORT=33306 DB_DATABASE=fabric_ppc_test \
DB_USERNAME=fabric DB_PASSWORD=secret ./vendor/bin/pest      # create fabric_ppc_test as root/root first
  • Suites: tests/Unit (no framework, e.g. BatchSplitter, Position), tests/Feature/<Module> (RefreshDatabase; the Oracle tests use the real 623-row fixture with exact counts), tests/Concurrency (MySQL-only, DatabaseTruncation, two connections — proves lot locks and snapshot handling; self-skips elsewhere), Vitest under resources/js/**/__tests__ (helpers, composables, mounted dialogs and the DetailGrid).
  • Current counts (P2, Task 10 tree): 443 Pest tests / 89 Vitest tests, phpstan 0 errors.

11 · Conventions (non-negotiable)

  • New PHP under App\Modules\<Module>\…; models under Models\*. Migrations 2026_09_19_ + 6-digit sequence from the task's reserved range.
  • No bare user-visible strings: PHP __('group.key'), Vue t('group.key'); each module owns its lang group, never mixed.
  • One route file per module; explicit routes above catch-alls.
  • Toasts via Inertia::flash then back(); delete errors reach form.setError(); "in use" only from a real FK violation (isForeignKeyViolation), other DB errors surface.
  • In-page record navigation through useUnsavedGuard().guard(fn). Never edit components/ui/*.
  • Quantities decimal(12,2), bcmath at scale 2; console/queue writes to audited models inside ImportCommitService::asAuditUser().
  • Workflow: subagent-driven development — one implementer per plan task, a spec/quality reviewer, fix rounds, a final whole-branch review. Judgment calls are recorded as rulings in docs/HANDOFF.md.

13 · Go-live checklist

  • PHP 8.3+ with ext-bcmath, pdo_mysql; MySQL 8.4; Redis 7; Node 22 for the asset build.
  • php artisan migrate --force on every deploy (first install: --seed), before config:cache (the admin seeder reads env()). Then config:cache, route:cache, view:cache, npm ci && npm run build.
  • Change the admin password after first login; deactivate the six demo users.
  • Queue worker under Supervisor/systemd: php artisan queue:work redis --timeout=600 --tries=1 --sleep=3, stopwaitsecs=660, restart after each deploy (queue:restart). REDIS_QUEUE_RETRY_AFTER ≥ 660.
  • Scheduler (cron * * * * * php artisan schedule:run) for the nightly ledger invariant check.
  • Uploaded Oracle exports are kept under storage/app/oracle-imports/ (no retention policy yet). HTTPS, rate-limited login and CSRF come from the kit.
