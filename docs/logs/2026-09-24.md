## 3. Two cross-database defects diagnosed

Both were masked by the project's gate running on SQLite while production runs MySQL.

1. **Text criteria case-sensitivity.** `QueryCriteria::text()` used `=` for wildcard-free values. SQLite's `=` is case-sensitive; MySQL's default collation is not. Fixed on `feat/p2-production` via `LOWER(col) op ?`.
2. **Date comparison.** SQLite stores `2026-09-11 00:00:00` in a `date` column while MySQL's `DATE` truncates, so `= '2026-09-11'` matches on one and not the other. **Still open** — it is the one remaining SQLite failure (`ProductionSheetScreenTest`).

Still missing from P2 Task 13: the **MySQL CI job**, two browser tests, and `tests/Browser/TmpTest.php` is committed debris.

## 4. Oracle source analysis

Analysed `docs/queries.txt` (3 tables + 1 view supplied by the client) → **`docs/planning/findings.md`**.

Central finding: **Oracle has no status column anywhere.** Status splits in two —

- **Derivable** (data present, field missing): current location = latest `PROCESSING_LOTS.TO_CC_CODE`; metres per cost centre = arrivals − departures; full operation history.
- **Absent entirely** (must be captured by this app): planned route, hold/cancel/close, colour approval, dispatch, loss, and "waiting vs in progress" (a row appears only when an operation *finishes*).

Defects found in the client's own `processing_lots_trans` view:

- **Join fan-out** — both `PROCESS-*` branches join on `LOT_NUM` alone, which is not unique. Quantities inflate where a lot number recurs across contracts.
- `PC_DTL_ID` (the only reliable key) is not in the view's output.
- Hard-coded `'01-SEP-26'` string compared to a `DATE`.
- No dispatch or loss rows, so balances cannot close.

Not supplied and needed: `PROCESSING_CONTRACT_M`/`_D` DDL, and every code master (cost centre, machine, operation, design, colour, version, location, section, user).

## 6. Security defects found by review — both fixed

1. **M-1** — the gate allow-listed `verification.notice`, and Fortify renders it via Inertia. A pending+unverified user holding the admin role received a 200 with `data-page`, their own user row, **all 28 permission names** and the JS bundle preloaded. Fixed by removing that route from the allow-list; the pending screen already carries verification state.
2. **M-2** — `TrackDevice` ran for guests, so every cookieless request created a `user_devices` row **and** an audit row. Ten curls at the public `/i18n/en.json` added 10 of each — an unauthenticated table-fill vector. Fixed: rows are only created for authenticated users.

Six lesser issues also fixed: a fabricated console IP in the action log, a date-range boundary bug losing the last day, a missing index on a filtered column, an attribution asymmetry on user deletion, a `$extra` array-merge precedence bug, and a duplicated query.
